# Independent Code Audit — Toolbox Vault Web (Phase 1)

**Date:** 2026-10-16
**Auditor:** independent review agent (did not write this code)
**Scope:** `backend/` (FastAPI + SQLAlchemy + Alembic), `frontend/` (React + TypeScript + Vite), `docker-compose.yml`, Dockerfiles, nginx template, GitHub Actions deploy workflow
**Spec:** architecture blueprint §4 (module laws), §6 (auth), §11 (security plan), §12 (performance budgets)

The headline lesson of this audit: **every static gate passes, and the code is still broken at runtime in three places.** Compile/typecheck/build gates cannot see inside function bodies or route tables. Two of the Critical findings below are one-line bugs that any single smoke test would have caught — and the repo contains no tests at all (see Important 7).

## CRITICAL — must fix before any deployment

### C1. Signup crashes at runtime: `func` is used but never imported
- `backend/app/modules/core/service.py:40` — `_next_account_number()` calls `select(func.nextval("account_number_seq"))`, but the module imports only `select` from SQLAlchemy (lines 12–18). Reproduced directly: calling the function raises `NameError: name 'func' is not defined`.
- Effect: **every `POST /api/core/signup` returns HTTP 500.** The single most important flow in the product does not work. It survived because compileall and app-import never execute function bodies. Fix is one import line — but nothing should deploy until a smoke test proves signup end-to-end.

### C2. `GET /field-definitions` is unreachable — shadowed by `GET /{tool_id}`
- `backend/app/modules/inventory/routes.py:85` registers `GET /{tool_id}`; the `GET /field-definitions` route is registered later (line ~152, at the bottom of the file). Starlette matches in registration order and `/{tool_id}` matches the literal segment `field-definitions` first — proven with Starlette's route matcher against the router's own route table (first FULL match: `get_tool`). The request then fails UUID validation with a 422.
- Effect: the field-definition list **never returns**. Both frontend consumers break at runtime: `frontend/src/modules/inventory/ToolFormPage.tsx:61` and `ToolDetailPage.tsx:31`. The author knew this trap — the `/search` route carries a comment about exactly it (routes.py:30) — and the later-appended definitions block fell into it anyway. Custom fields are a headline Phase 1 feature; their read path is dead.

### C3. Presigned URLs are signed for the internal MinIO host, then hostname-swapped — signatures will not validate in the production topology
- `backend/app/core/storage.py:87-115` — `presigned_put_url` / `presigned_get_url` generate URLs with a boto3 client bound to `settings.minio_endpoint` (`http://minio:9000`), then `_public_url()` string-replaces that endpoint with the public one (`https://files.toolboxvault.com`).
- SigV4 presigned URLs sign the `Host` header. The signature is computed for host `minio:9000`; the browser presents the URL to `files.toolboxvault.com`, and nginx forwards it with `proxy_set_header Host $host` (`frontend/nginx.conf.template`, files server block). MinIO recomputes the signature against the public host → `SignatureDoesNotMatch` → **403 on every browser upload and every photo/document download** in the intended deployment. Forwarding the path unchanged (which the template correctly does) is necessary but not sufficient.
- Server-side storage operations (HEAD verify, delete) use the internal client directly and are fine — which makes this easy to miss: the API will happily verify objects the browser could never have uploaded.
- Fix direction: sign with a second boto3 client configured with the public endpoint. Caveat: Docker/MinIO are unavailable here, so this is proven by the signing mechanism, not by a live request — it must be the first thing verified on the server.

### C4. Field definitions are global, and any user can destroy every other user's custom data
- `backend/app/modules/inventory/models.py` — `FieldDefinition` has **no `owner_id`**; definitions are platform-global. The routes (`inventory/routes.py:152-210`) let **any authenticated user** create, update, and delete them.
- `backend/app/modules/inventory/custom_fields.py:71-85` — `delete_definition()` runs an UPDATE stripping that definition's key from **every tool in the database**, with no tenant scoping (none is possible — the schema has no owner concept).
- Effect: any single account can (a) delete a definition and permanently strip that field's values from all users' inventories, or (b) create a definition with `required=true`, which `validate_custom_data` (custom_fields.py:126-134) then enforces globally — **blocking tool creation for every user on the platform**. This contradicts the product vision (per-user customizable fields) and is a cross-tenant data-integrity hole, not a cosmetic issue. It needs a design decision (per-user definitions, or admin-only global definitions) and a schema change — the only Critical that isn't a one-liner.

## IMPORTANT — fix before public launch; schedule immediately after the Criticals

### I1. No brute-force protection or password policy on auth
- `backend/app/modules/core/routes.py:33-42` — `/login` has no rate limiting (no limiter exists anywhere in the codebase; grep-verified). Blueprint §11 explicitly requires brute-force rate limiting on login.
- `backend/app/modules/core/schemas.py:12` — `password: str` with no minimum length or any policy. A one-character password is accepted at signup.

### I2. Email verification does not exist
- `backend/app/modules/core/models.py` has `email_verified`, defaulting to `False` — and nothing in the codebase ever sets it to `True` or checks it. There is no verification endpoint, no verification email, and login does not require it. Blueprint §6 specifies a verification link at signup and §11 requires verified email for sensitive actions. Accounts are currently verified by nothing more than claiming an email address — which also undermines the planned migration (accounts matched by email) and the referral system.

### I3. Sessions hard-expire after 30 minutes; no refresh/rotation
- `backend/app/core/config.py:18` sets a 30-minute access token; `core/security.py` mints only access tokens; there is no refresh token, no rotation, no renewal endpoint. Blueprint §6 specifies "short-lived JWTs **with rotation**." As built, every user is forcibly signed out mid-work every 30 minutes (the frontend deletes the stored token on the first 401 — `AuthContext.tsx` load effect). Either implement refresh rotation or consciously re-spec the session length; the current combination is the worst of both.

### I4. Default secrets fail open — no startup guard
- `backend/app/core/config.py:14-22` — if env vars are absent, the app boots with `jwt_secret = "change-me"`, a database URL containing `change-me`, and MinIO password `"change-me"`. Nothing refuses to start. The production `.env` is created by hand on the server; one omitted line silently yields a **publicly known JWT signing secret** (it is printed in the source), i.e. forge-any-user tokens. The app should fail closed: refuse to start when secrets equal the shipped defaults.

### I5. The API connects to object storage with the MinIO **root** credentials
- `backend/app/core/storage.py:53` builds the boto3 client from `settings.minio_root_user` / `minio_root_password`. A compromise of the API service is a compromise of the entire storage layer (all buckets, all users' files, delete anything). Blueprint §11 requires least-privilege. The app needs its own bucket-scoped credentials. (Related, lower grade: the API also connects to Postgres as the database-owning user — §11's least-privilege DB roles are not implemented; acceptable for Phase 1 if tracked.)

### I6. `tools.owner_id` has no index
- `backend/app/modules/inventory/models.py:70` declares the FK without `index=True`; the migration creates no index on it either (grep-verified: the only tools index is the GIN search index). **Every** list, search, and detail query filters by `owner_id`, so each one is a sequential scan whose cost grows with total platform tools — directly against the §12 budget (search < 500 ms at 100k tools). One-line fix in a follow-up migration.

### I7. There are no automated tests anywhere in the repository
- Find/grep-verified: zero test files, zero test configuration, frontend and backend. The verification story is compile + typecheck + build — and Criticals C1 and C2 both sailed through all three. A minimal smoke suite (signup → login → create tool → list definitions → search) would have caught both before this audit. This is the process root cause of the Critical list.

### I8. Dependencies are not locked anywhere
- `backend/requirements.txt` — every dependency is a `>=` range ("pinned loosely on purpose"). `frontend/Dockerfile` runs `npm install` after copying only `package.json` — `package-lock.json` is not present at install time, so it isn't honored. Every server build can silently pull a new, breaking release of FastAPI/Pydantic/React, and the deploy pipeline rebuilds from these ranges on every push. A routine content commit can take production down. Pin the backend (exact versions or a lock/constraints file) and switch the frontend to `npm ci` with the lockfile copied first.

### I9. No security headers at the edge
- `frontend/nginx.conf.template` contains **zero** `add_header` directives (grep-verified). Blueprint §11 requires strict CSP headers (plus HSTS). Nothing sets Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, or Referrer-Policy on either server block. (Justified deviation, noted for the record: §11 also lists CSRF tokens, but auth is via `Authorization`-header bearer tokens rather than cookies, so classic CSRF does not apply; CSP is the real gap.)

### I10. Law 4 (service interfaces only) is breached in the seams
Blueprint §4, Law 4: modules never import another module's internals; cross-module access goes through service interfaces.
- `backend/app/modules/inventory/routes.py:15` — `from app.modules.core import models as core_models`. It is used only as a type annotation, but it is exactly the prohibited import, in the codebase that elsewhere prides itself on avoiding it (`core/deps.py` docstring).
- Structurally deeper: `core/deps.py:36-51` `get_current_user` — the sanctioned path every module uses — returns core's **ORM `User` model instance**. The "service interface" therefore leaks core's table shape to every consumer; a core model refactor ripples everywhere Law 5 says it shouldn't.
- Frontend mirror: inventory pages deep-import `../core/auth/RequireAuth` (`ToolListPage.tsx:5`, `ToolDetailPage.tsx:5`, `ToolFormPage.tsx:5`) because core exposes no public surface (no index export).
None of this bites today with two modules. It will compound with every added module, which is precisely what the law exists to prevent. Define public surfaces (a DTO from `get_current_user`; a core `index.ts` export) before Phase 2 adds consumers.

## MINOR — real, but not launch-blocking

- **M1. `updated_at` never updates.** `inventory/models.py` gives it only `server_default=func.now()`; there is no `onupdate` and no trigger bumps it. It will forever equal `created_at` — and search's default ordering (`search.py`, order by `updated_at desc`) is silently just creation order.
- **M2. Partial custom-data updates fail required-field validation.** `custom_fields.py:106-134` validates required fields against only the submitted dict; a client updating one custom field without resubmitting all required ones gets a 422. The current frontend always sends the full object, masking it — the API contract is still wrong.
- **M3. Schema/DB bound mismatches turn user input into 500s.** `inventory/schemas.py` puts no length caps on strings that the DB caps (`String(300)`, `String(200)`, `String(50)`), and `Decimal` fields have no range checks against `Numeric(12, 2)` or negativity. Overlong names / absurd prices raise database errors (500) instead of 422s.
- **M4. Upload size is not bounded at issuance.** The presigned PUT carries no content-length constraint; the 10 MB cap is enforced only at attach time (`attachments.py`). Oversized objects land in the bucket and orphan if never attached — a slow storage-abuse leak. No content sniffing or malware scan either (§11 asks for a scan); content type is whatever the client declared at PUT and MinIO stored.
- **M5. Registry doesn't do what its docstring claims.** `modules/registry.py:24-35` says "dependency-safe order," but there is no topological sort — modules yield in dict order, and the `seen` set is written and never read. Harmless with two modules; Law 6's "visible blast radius" is currently just declared dependencies (which do exist and are validated for presence — credit that).
- **M6. JWT stored in `localStorage`.** `frontend/src/lib/api.ts` / `AuthContext.tsx` — deviates from §11's secure-cookie plan; any future XSS becomes full session theft. Compounds I9 (no CSP).
- **M7. Auth edge-case robustness.** `core/security.py` decode: `payload["sub"]` raises `KeyError` (uncaught — only `PyJWTError` is caught) on a sub-less token; `verify_password` catches only `VerifyMismatchError`, so a malformed stored hash raises instead of returning False; `core/service.py:23` `uuid.UUID(...)` raises `ValueError` on a non-UUID subject. All require server-minted inputs today, so impact is 500-instead-of-401 hygiene, not a live hole.
- **M8. Enumeration/race nits.** `core/service.py` `authenticate()` returns immediately for unknown emails (no dummy verify) — timing reveals whether an email is registered. Signup is check-then-create (`core/routes.py:23-30`); a concurrent duplicate signup hits the UNIQUE constraint and returns 500 instead of 409.
- **M9. Unbounded list + per-row URL minting.** `service.list_tools` returns all of a user's tools with no limit/pagination, and `serialize_tool` mints a presigned GET URL for every attachment of every row. Fine at Phase 1 scale; against §12 budgets at warehouse scale.
- **M10. Custom-field definition hygiene.** Definition `name` is documented as a slug but never validated as one (spaces/case allowed); name lookups are case-sensitive, so `VIN` and `vin` can coexist and collide in the `by_name` map. `update_definition` can change `field_type` without revalidating already-stored values.
- **M11. Search reindex gap (documented tradeoff, confirmed).** The trigger fires only on `tools` writes; toggling a definition's `searchable` flag or label does not rebuild existing vectors. Acceptable for Phase 1, but it should be a named backlog item, not a surprise.
- **M12. Compose/Docker nits.** `minio/minio:latest` unpinned (only unpinned image); the `api` service doesn't depend on MinIO, so a first-ever upload can race MinIO readiness and surface a 422; backend image runs as root; uvicorn runs without `--proxy-headers`, so anything later keyed on client IP (rate limiting, logs) will see the nginx container's IP.
- **M13. Deploy pipeline has no check gate.** `.github/workflows/deploy.yml` rsyncs and rebuilds on every push with no compile/test/build step first. A broken push is discovered by the server build (old containers keep running — the one saving grace), not by CI.
- **M14. Frontend spacing literals.** Colors are impeccably token-driven (zero hex values outside `theme/` — grep-verified), but layout values are hard-coded inline across pages (`0.75rem`, `140px` grid columns in `AccountPage.tsx:7`, etc.) instead of spacing tokens/shared layout primitives. Law: "no raw styling in module code" — honored for color, half-honored for spacing.
- **M15. Migration/model drift (harmless today).** The migration gives `id` columns `server_default=gen_random_uuid()` while the models use Python-side `uuid4` defaults; the `account_number_seq` Sequence is declared both in migration SQL and model metadata. Under the Alembic path everything is consistent; a future `create_all` dev shortcut would double-create the sequence. Worth a comment, not a fix.

## CLEAN — verified good, credit where due

- **Password/JWT primitives are done right and centralized.** `core/security.py` is the only place touching argon2 or JWT; argon2id hasher; HS256 with the algorithm pinned on decode; 30-minute expiry. No module reimplements crypto (Law 2 honored).
- **No SQL injection surface.** Every query goes through SQLAlchemy ORM/parameterized expressions, including full-text search (`websearch_to_tsquery` with a bound parameter — no string-built SQL anywhere in app code; raw SQL exists only as static DDL in the migration).
- **Ownership checks are consistent.** Every tool read/update/delete and both upload endpoints resolve the tool and compare `owner_id` (`service.py`, `attachments.py`). Attach additionally binds the storage key prefix to owner+tool, HEAD-verifies the object's **real** size and content type against the allowlist, and never trusts the client's claims. This is the best-built part of the codebase.
- **Object-storage design honors the old app's lesson.** Keys only in the DB, bytes never transit the API or the database, read URLs minted fresh at serialization (`service.py` `serialize_tool`), filenames sanitized (`storage.py` `safe_filename`), tool deletion best-effort cleans up objects.
- **Migration ↔ models match.** Tables, columns, types, lengths, nullability, the `(item_type, name)` unique constraint, and the FK all agree. The search trigger implements the spec'd weights (name A; brand/model/serial B; notes + searchable custom values/labels C; condition/category/location D) with a GIN index, and the migration fires it once to backfill. Ryan's "apple in the notes" acceptance case is satisfied by construction. Account numbers use atomic `nextval` with a UNIQUE backstop — the design is right; only the import (C1) is wrong.
- **No god files; structure matches the blueprint.** Largest file in the codebase is 356 lines (`ToolFormPage.tsx`); largest backend file 210. `main.py` is a pure factory; modules split routes/service/models/schemas as the laws require; the registry validates declared dependencies at startup; the `_template/` module documents the add-a-module path.
- **Shared components are genuinely shared.** Both modules consume `frontend/src/components/` via its index; zero copied hex colors outside the theme layer; zero `dangerouslySetInnerHTML`; module routes lazy-load (separate chunks in the production build); nav ordering is registry-config-driven (Law 7, code-level).
- **Infra hygiene.** Only port 80 is published; Postgres and MinIO are not exposed; `.env` is gitignored and absent from the repo; the deploy workflow excludes `.env` from rsync and never overwrites it; the backend Dockerfile migrates before serving.

## VERDICT

**Not safe to deploy as Phase 1 in its current state.** Four Critical findings stand between this code and a working launch, and two of them break the product's front door: nobody can sign up (C1), the custom-field read path is dead (C2), and in the intended production topology no browser photo upload or download would survive signature validation (C3). C4 is worse than a bug — it's a standing cross-tenant data-destruction capability handed to every account.

The encouraging part, stated plainly because it's true: **the architecture is sound and three of the four Criticals are small, surgical fixes** — one import line, one route reordering (move the field-definition routes above `/{tool_id}`), one additional signing client bound to the public endpoint. C4 needs a design decision (per-user definitions vs. admin-only globals) plus a schema change, and should be made before real users' data exists to lose. Add the I4 fail-closed secret guard to the same pass — it's five lines and it removes the only total-compromise footgun.

**Minimum bar before first deploy:** C1–C4 fixed, I4 fixed, and one end-to-end smoke test (signup → login → create tool → upload photo → search) run against the real Docker stack on the server — because until that happens, this codebase has never actually run anywhere, and this audit's two runtime proofs show exactly what "never run" hides. The remaining Important items (rate limiting, email verification, refresh tokens, the `owner_id` index, locked dependencies, a starter test suite) are a legitimate immediate-follow list for the first weeks of operation, not a reason to delay once the Criticals close.
